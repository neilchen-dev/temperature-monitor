## 结论摘要

1. 当前台账原先没有独立的“环境标准版本表”；本轮已在同一 Base 新建 `环境标准表`，将标准版本从 `设备温湿度记录` 主表中分离。现已导入 TH-01～TH-11 的历史限值，并全部启用；每条记录通过 `适用设备` 绑定监测点。
2. 受控作业的输入入口是 `环境受控作业登记（试验）`，但该表当前为 0 条记录；4 条 TH-03/04/05/07 工作流已经定义了作业开始、工艺切换、结束时如何回写主表和作业区间表，但生产运行证据尚不充分。
3. 飞书公式字段是当前业务表现的一部分，但不应直接当成 Python 的领域真相。Python 应复刻其可观察语义，并把原始值、规则版本和计算结果分别保存。
4. **规则已冻结为 5 分钟**。主表字段说明、责任人说明仍写 10 分钟，属于待清理的旧说明，不再作为 Python 实现依据。
5. 同设备可以同时保留多条尚未人工闭环的历史事件；只有同一报警周期（同监测点、同开始时间）产生多条记录才属于 `EVENT_DUPLICATED`。
6. Python 已加入作业登记、环境异常事件和仓库点检三类新增写入适配器；默认关闭，只有 `AUTOMATION_MODE=active` 且 `FEISHU_WRITE_ENABLED=true` 才允许这些适配器写入。

### 3.3 当前飞书实际判定优先级

`设备温湿度记录.当前判定状态` 公式体现的优先级是：

1. 温度或湿度判定为 `离线` → `设备离线`。
2. 温度或湿度为 `数据缺失` 或 `数据异常` → `数据异常`。
3. `控制类型=仅监测` → `仅监测`。
4. `控制类型=作业期间控制` 且 `当前作业状态≠作业中` → `仅监测`。
5. 任一适用温湿度上下限为空 → `待工艺标准`。
6. 温度、湿度均为 `正常` → `正常`。
7. 其他情况 → `超限`。

边界是闭区间：等于上下限时通过。温度和湿度判断先 `VALUE`，再 `ROUND(..., 1)`，然后与上下限比较。

### 3.4 已确认的规则冲突

- 主表 `温度判定` 的字段说明声称会把华氏度转换为摄氏度，但当前公式只是 `VALUE` 加四舍五入，没有发现华氏度转换。Python 必须先确认传感器真实单位，不能只按字段说明实现。
- 主表当前限值看起来是已经解析后的“当前适用值”，但在现有表结构和工作流中没有看到它们从哪个标准文件/版本计算出来；它们不再作为完整标准版本库。
- 新标准表已建立，Resolver 规则冻结为：有效期、启用、区域匹配、设备精确匹配、作业类型精确匹配、优先级和冲突报错。同一区域允许多个监测点分别绑定不同标准。

`FeishuStandardAdapter` 只负责按显式字段映射读取和规范化；实际 HTTP source 为
`FeishuBitableRecordSource`，复用项目现有 tenant token、重试和分页服务。标准表本身
不包含写入路径；作业、异常、点检写入集中在 `integrations/feishu_writers.py`。

### 3.5 建议的标准同步契约

飞书标准台账（或经过确认的标准来源）→ `StandardSyncService` → 字段校验 → SQLite `standard_versions` → 原子激活 → `SQLiteStandardResolver`。

同步校验至少包括：上下限成对且 `min <= max`、时间范围合法、版本唯一、同一匹配键的有效期不冲突、来源文件非空、优先级明确。同步失败时继续使用上一版有效标准，并记录同步错误；不能让一次飞书误编辑直接改变生产判定。

### 4.2 动作到领域状态

| 飞书动作/值 | `OperationState` 建议映射 | 飞书副作用 |
|---|---|---|
| `开始作业` | `OPERATING` | 新增作业区间；主表改为 `作业中`；写入当前工艺、作业开始时间；按报警状态决定是否继续计时 |
| `工艺切换` | 仍为 `OPERATING`，但产生一次区间切换 | 旧区间以 `工艺切换结束` 结束；新建一个 `作业中` 区间；更新主表当前工艺和开始时间 |
| `结束作业` | `IDLE` | 结束开放区间为 `已结束`；主表改为 `无作业`、工艺置 `N/A`、清空作业开始时间；只清理 `计时中` 报警 |
| `无作业` | `IDLE` | 当前主表显示值，不是动作事件 |
| `N/A` | `NOT_APPLICABLE` | 已冻结：不能等同 `IDLE` |
| `暂停` | 不支持 | 已冻结：第一版不实现 `PAUSED` |

### 4.3 乱序和新旧记录

- 登记表有 `提交时间`（创建时间）和 `状态记录时间`，但 4 条作业工作流在写入区间开始/结束快照时使用的是触发记录的 `recordCreatedTime`。
- 已冻结：按飞书记录创建时间判断新旧；当前工作流没有实现该保护，旧的结束登记理论上可能覆盖新的开始状态，Python Adapter/Application gate 必须拒绝这种覆盖并记审计。
- `设备温湿度记录.更新时间` 被超限流程用作连续超限开始时间，但并未形成通用的版本校验或 watermark。
- **建议**：Python 入口强制带 `source_record_id`、`source_created_at`、`source_updated_at`，按设备/区域保存最后接受的版本；时间倒退时只记录审计，不覆盖当前状态。

`integrations/feishu_writers.py` 以当前台账字段为唯一写入映射，底层使用带资源锁、Token 刷新和退避重试的 Base API 原语：

| 能力 | 写入表 | 关键行为 |

### 5.2 规则细节

#### A. 作业状态同步（#12~#15）

4 条工作流是同一套逻辑，只是把监测点固定成 TH-03、TH-04、TH-05、TH-07。登记表的 `登记组合校验` 先验证“监测点-区域-工艺”的组合；只有 `有效` 才继续。

- 开始：登记当前温湿度、在线状态和判定；新增 `作业中` 区间；主表改为 `作业中`，回写当前工艺和作业开始时间。
- 工艺切换：先结束开放区间，结束状态为 `工艺切换结束`；再新增一个 `作业中` 区间；更新主表当前工艺和开始时间。
- 结束：结束开放区间，结束状态为 `已结束`；主表改为 `无作业`、工艺置 `N/A`、清空作业开始时间；只清理 `计时中`，不清理已经 `已发警报` 的状态。
- 区间记录保存开始/结束时的温湿度、在线状态、温湿度判定和登记人。
- 当前试验登记表和区间表均为 0 条记录，因此以上是配置语义，尚未用生产样本验证。

#### B. 超限与恢复（#16~#17）

超限工作流的实际逻辑为：

1. 主表当前判定为 `超限`，报警状态为 `未触发`，且责任人非空；控制条件是“当前作业中”或“全天控制”。
2. 立即把报警状态改为 `计时中`，连续超限开始时间写触发记录的 `更新时间`。
3. **实际 Delay 5 分钟**。
4. 重新查主表，以当前值复核：仍为 `超限`、仍为 `计时中`，且“作业中”或“仓库点检对象=是”。
5. 复核通过：向异常事件表写入监测点、区域、开始时间、控制要求、峰值温湿度、责任人、触发温湿度判定；主表置 `已发警报`；向责任人发送消息。
6. 复核失败：报警状态重置为 `未触发`，清空连续超限开始时间。

恢复工作流在非超限且报警处于 `计时中`/`已发警报` 时触发，先等待 1 分钟再重新读取主表。计时中的报警在恢复后清空，并查找同设备、恢复时间为空的事件写入恢复时间。已发警报的分支若仍满足复核中的保护条件则中止重置；这部分需要结合实际事件关闭流程再做一次端到端确认。

#### C. 点检快照（#8~#11）

4 条工作流只有“区域→固定设备”的差异，应归并为一个参数化能力：

`sync_inspection_snapshot(area, device_id, inspection_record)`。

同步字段包括点检时间、温度、湿度、在线状态、环境判定、温湿度判定、异常说明和报警状态；同时把点检时间写回主表对应设备的 `最近仓库点检时间`。这 4 条流程本身不创建事件。

#### D. 点检异常建事件（#3）

该工作流当前停用。触发条件是以下任一项成立：

- `现场仓储状态` 为 `发现异常` 或 `待跟进`；
- `监测系统状态` 为 `离线/数据异常`；
- `未闭环环境报警` 为 `有` 或 `待确认`。

然后按防爆仓库、仓库、PE 仓库、设备区分支处理：查找同区域监测点的待处理/处理中事件；已有则通知责任人；没有则创建事件、获取自动编号、回填点检记录的 `异常/报警编号` 并通知。责任人目前硬编码为：防爆仓库/仓库/设备区→蔡周兵，PE 仓库→朱正。

这里有两个迁移风险：事件编号 `ENV-...` 是文本，而点检表的 `异常/报警编号` 字段类型是数字；另外按“已有事件”查找和当前事件表实际重复记录之间存在矛盾。

#### E. 提醒和人工闭环（#1、#2、#4、#5、#6、#7）

- 提醒类工作流主要发送飞书消息，不写业务状态；应先作为通知适配器保留。
- 6 小时未结束提醒依赖作业开始时间，触发时间为开始后 6 小时且提醒时间点为 09:00 的 ReminderTrigger 配置。
- 24 小时逾期由事件表公式 `NOW()-开始时间>=1` 判断，存在时区和公式刷新边界，需要 Shadow 记录实际触发时间。
- 闭环反馈通过异常编号查找待处理/处理中事件后直接关闭，没有额外的必填校验；完整性提醒是事后补救。

### 6.1 领域边界

`evaluate_monitor_state()` 必须是纯规则函数：相同输入产生相同输出，不读数据库、不发飞书、不创建任务、不等待、不改变报警状态。

推荐链路：

```text
Sample
  -> OperationState
  -> StandardResolver
  -> EnvironmentStandard
  -> monitor_engine.evaluate
  -> MonitorResult
  -> AlarmStateMachine
  -> Domain Actions
  -> Application Action Mapper
  -> automation_tasks / events / Feishu Adapter
```

`MonitorResult` 描述一个采样时刻；`AlarmState` 描述生命周期；`Event` 描述业务事件；三者不能互相替代。

### 7.1 作业状态

| 飞书值 | Python 建议值 | 说明 |

### 7.2 温湿度与总体判定

| 飞书值 | Python 建议值 | 说明 |
|---|---|---|
| `正常` | `NORMAL` | 在适用标准内 |
| `低于下限` | `LOW` | 低于对应下限 |
| `高于上限` | `HIGH` | 高于对应上限 |
| `超限` | `VIOLATION` | 总体存在温度或湿度超限 |
| `待工艺标准` | `NO_STANDARD` / `UNKNOWN` | 不能当作正常；主表有任一限值为空时出现 |
| `仅监测` | `NOT_APPLICABLE` | 当前不进入作业期间控制报警判定 |
| `设备离线` | `OFFLINE` / `UNKNOWN` | 建议与普通未知数据区分 |
| `数据异常` | `DATA_ERROR` / `UNKNOWN` | 建议与离线区分，便于审计 |
| `数据缺失` | `MISSING` / `UNKNOWN` | 当前温度或湿度为空 |

Python `MonitorResult` 已增加 `applicability` 和 `data_quality`，可区分仅监测、无标准、离线、缺失和数据异常；总体 `NORMAL` 只代表适用且数据质量良好时的合格结果。

### 7.3 报警和事件

| 飞书值 | Python 建议值 | 语义 |
|---|---|---|
| 报警 `未触发` | `AlarmState.NORMAL` | 没有待验证或已发报警 |
| 报警 `计时中` | `AlarmState.PENDING` | 已出现超限，等待持久化复核任务 |
| 报警 `已发警报` | `AlarmState.ALARM` | 已创建/发起环境异常事件 |
| 事件 `待处理` | `OPEN` | 事件存在，尚未开始处置 |
| 事件 `处理中` | `IN_PROGRESS` | 已进入人工处置 |
| 事件 `闭环状态=已闭环` | `business_closed=True` | 公式字段给出的最终业务闭环判据 |
| 事件 `恢复时间` 非空 | `RECOVERED` 事实 | 环境已恢复，不等于事件关闭 |

`恢复正常` 与 `事件闭环` 不是同一个概念：前者是监测事实，后者由只读公式字段 `闭环状态` 最终判定。Python 不写该字段，也不从 `NORMAL`、`恢复时间` 或 `关闭完整性校验` 推导闭环。

### 7.4 空值语义

- 任一适用上下限为空：当前公式在非“仅监测”情况下判为 `待工艺标准`，不等价于“没有限制”。
- `连续超限开始时间` 为空：没有正在进行的连续超限计时。
- `恢复时间` 为空：事件尚未被自动记录为恢复，不能直接表示环境仍超限。
- `关闭时间` 为空：事件没有完成关闭。
- `作业开始时间` 为空：当前没有可用于 6 小时提醒的作业起点。
- 责任人为空：当前超限工作流不创建自动警报；这属于配置缺失，不应悄悄当成正常。
- `无作业` 与 `已结束` 不等价：前者是当前主表状态，后者是某一条区间记录的终态。

## 9. Shadow 比对规则

### 9.1 比较对象

不能把 Python 的一个字段直接和飞书一个公式字段硬比。建议两边都先规范化为：

```text
ObservedAutomationState(
    device_id,
    area_id,
    operation_state,
    operation_type,
    monitor_applicability,
    temperature_status,
    humidity_status,
    overall_status,
    standard_id,
    standard_revision,
    alarm_state,
    active_event_count,
    active_event_ids,
    observed_at,
)
```

Python 的 expected 由 `StandardResolver + monitor_engine + AlarmStateMachine` 产生；飞书的 observed 由主表、作业登记/区间表、事件表和点检表通过 `FeishuObservationAdapter` 读取。比较器不应知道飞书原始字段名。

### 9.2 规范化映射

- `当前作业状态=作业中` → `operation_state=OPERATING`。
- `当前作业状态=无作业` → `operation_state=IDLE`。
- `当前判定状态=超限` → `overall_status=VIOLATION`。
- `当前判定状态=仅监测` → `monitor_applicability=NOT_APPLICABLE`，不能直接算环境正常。
- `当前判定状态=待工艺标准` → `overall_status=NO_STANDARD`。
- 主表 `警报状态=计时中/已发警报` → `alarm_state=PENDING/ALARM`。
- `ALARM` 的观察证据应同时包括：主表已发警报和至少一个仍有效/未关闭的 ENV 事件；不能只比较 `当前判定状态=超限`。
- `active_event_count` 必须统计同设备/同异常轮次的未关闭事件，而不是只取第一条。

### 9.3 Diff 类型

| diff_type | 判定条件 |
|---|---|
| `MATCH` | 必需字段都存在，状态、标准和事件数量在允许延迟窗口内一致 |
| `STANDARD_MISMATCH` | 标准编号/版本不同，或上下限不同，或一边有标准另一边为 `NO_STANDARD` |
| `OPERATION_STATE_MISMATCH` | `OPERATING/IDLE/NOT_APPLICABLE` 不一致，或工艺上下文不同 |
| `ALARM_STATE_MISMATCH` | `NORMAL/PENDING/ALARM` 不一致，且不是可解释的时间窗口延迟 |
| `OVERALL_STATUS_MISMATCH` | 总体判定 `NORMAL/VIOLATION/UNKNOWN` 不一致 |
| `APPLICABILITY_MISMATCH` | 标准适用性 `APPLICABLE/NOT_APPLICABLE/NO_STANDARD` 不一致 |
| `DATA_QUALITY_MISMATCH` | 数据质量 `GOOD/OFFLINE/MISSING/ERROR` 不一致 |
| `TEMPERATURE_STATUS_MISMATCH` | 温度分项判定不一致 |
| `HUMIDITY_STATUS_MISMATCH` | 湿度分项判定不一致 |
| `EVENT_MISSING` | Python 期望 `ALARM`，但飞书没有对应未关闭事件 |
| `EVENT_DUPLICATED` | 对同一设备/异常轮次，飞书存在两个或以上未关闭事件 |
| `FEISHU_DELAY` | Python 已进入新状态，飞书仍等于上一份 Python expected，且两侧记录时间的绝对偏差在允许同步窗口内 |
| `UNKNOWN` | 缺设备映射、缺标准、缺时间、字段类型错误或无法确定观察结果 |

优先记录 `EVENT_DUPLICATED` 和 `EVENT_MISSING`，再记录状态差异；否则一个重复事件可能同时制造很多无效的 `ALARM_STATE_MISMATCH`。

### 9.4 Shadow 运行记录

每次运行建议记录：设备、采样时间、Python 标准和结果、Python 报警转换、飞书观察状态、比较结果、差异详情、读取延迟、规则版本、adapter 版本。建议连续观察至少 7 天，统计：规则一致率、状态转换一致率、重复事件数、漏事件数、飞书观察延迟、未知结果数。

同设备两条未闭环事件若属于不同报警开始时间，是允许保留的历史业务事件；若开始时间相同，Shadow 必须固定产出 `EVENT_DUPLICATED`。

## 10. 暂不迁移项

以下能力即使业务规则已经冻结，在真实标准表、只读观察接线和 Shadow 证据完成前，也不建议切换为 Python Active：

1. **不直接把 `设备温湿度记录` 当标准版本库**。独立 `环境标准表` 已建立，但模板记录仍禁用；正式标准必须经过来源确认和 StandardSyncService 校验。
2. **不关闭 17 条飞书工作流**。先 Shadow；#16/#17 按冻结的 5/1 分钟规则比对，#3 仍保持停用。
3. **不把人工闭环表单全部迁走**。闭环反馈、原因、措施、产品影响仍适合先保留在飞书；Python 只做规范化读取和 Shadow。
4. **不先迁移提醒消息的用户体验**。点检提醒、6 小时提醒、24 小时提醒、资料完整性提醒可以继续由飞书发出，Python 先记录 expected action。
5. **不自动替代点检异常建事件工作流**。当前 Python 点检写入已支持快照，但 `异常/报警编号` 的数字类型与 ENV 编号、区域责任人和历史重复事件仍需业务治理。
6. **不把飞书公式字段直接写成 Python 权威状态**。保留原始输入、Python 结果和飞书观察值，三者分开审计。
7. **不使用进程内 `sleep()` 实现 Delay**。所有延迟复核必须进入持久化任务表，具备 `due_at`、lease、重试和幂等键。
8. **不直接接管全部作业工作流**。当前 Python 已能创建作业登记并在 Active 中处理异常事件，但主表/区间表的全量生产替代仍需端到端验证；旧记录只审计、不覆盖当前状态。

## 已冻结规则与仍未实现项

以下 10 项已经人工确认，作为第一版 `rule_version=1.0` 契约；它们不再是待确认项：

1. 标准来源改为新建独立环境标准数据表，不使用主表当前上下限作为完整版本库；同一区域的不同监测点可绑定不同标准。
2. 连续超限正式报警确认时间为 5 分钟，恢复确认时间为 1 分钟。
3. `N/A` 表示 `NOT_APPLICABLE`，不能等同 `IDLE`；第一版不支持 `PAUSED`。
4. 正式作业登记入口为 `环境受控作业登记`。
5. 工单号选填；当前物理试验表尚无该字段时保留为空。
6. 作业登记按记录创建时间判断新旧；旧记录只记录审计，不覆盖当前状态。
7. 同一设备同时最多一个未关闭 ENV 事件；Python/SQLite 用数据库约束保证。
8. Shadow 状态更新延迟阈值为 60 秒；observed 等于上一份 Python expected 且双向时间偏差 ≤60 秒时记 `FEISHU_DELAY`，否则记真实 mismatch。
9. `EVENT_DUPLICATED` 与 `EVENT_MISSING` 优先于普通 `ALARM_STATE_MISMATCH`。
10. 本轮不修改既有飞书事件、工作流和正式业务状态；代码已提供受开关保护的写入能力，默认不执行。

仍未实现或需要未来配置的项：

- 新标准表中历史迁移记录对应的正式标准编号、版本、生效时间和来源文件条款；当前 11 条记录已启用供试运行观察，正式来源仍需确认。
- 设备运行期区域切换历史、标准来源文件的具体条款内容。
- 点检表 `异常/报警编号` 的业务关联方式和历史重复事件的业务处置。
- 作业主表/区间表的全量生产接管、通知迁移和端到端 Active 证据。
